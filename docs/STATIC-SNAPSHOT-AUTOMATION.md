# Автоматическое обновление статического снимка

## Что включено

Текущая отправка снимка переводится на согласованное владельцем GitHub App
**5872216**. Область токена, исключение защиты и оставшаяся сквозная проверка
описаны в [SNAPSHOT-APP-PUSH.md](SNAPSHOT-APP-PUSH.md).

`.github/workflows/update-static-snapshot.yml` после слияния в `main` запускается
ежедневно в **03:00 UTC / 06:00 Москвы**, а также вручную через `workflow_dispatch`.
GitHub может задерживать плановый запуск. Ручной запуск допускает обновление только
с ветки `main`.

Для чтения нужны repository secret `SNAPSHOT_SUPABASE_READ_KEY` и variable
`SUPABASE_URL` (инструкция ниже). Владелец уже добавил их; работа через реальные
значения подтверждена Actions, включая прогон 45003492254. Секреты не созданы агентом
и их значения не извлекаются через API. Для отправки также нужны реквизиты App из
[SNAPSHOT-APP-PUSH.md](SNAPSHOT-APP-PUSH.md). Права интеграции Arena не расширялись.

Скрипт вызывает только `export_static_snapshot_v1()` без параметров. RPC читает
последнюю сохранённую строку каждого из трёх фиксированных инструментов:

| Тикер | ID в базе | Смысл наблюдения |
| --- | --- | --- |
| BZ=F | `brent_yahoo_bzf` | Brent, ближайший фьючерс NYMEX; дата сессии Yahoo без времени |
| ^GSPC | `sp500_yahoo_gspc` | S&P 500; дата сессии Yahoo без времени |
| XAU | `gold_api_xau_observed_daily` | Спот XAU/USD; последнее сохранённое наблюдение за UTC-сутки с `price_timestamp`, не официальный close |

Числа передаются из `numeric` как строки `price::text`, без округления. Источник,
тип инструмента, валюта, единицы и периодичность проверяются строго. Отсутствие,
дубликат, неверное число/календарь, будущее наблюдение или возраст **больше семи
UTC-календарных дней у любого инструмента** останавливают весь экспорт. Седьмой
день включён; возраст считается отдельно для каждой строки, не по `exportedAt`.
RPC не выбирает более старую «удобную» строку вместо некорректной последней.

Время экспорта берётся из того же запроса к базе. Расхождение времени экспорта
с часами runner более пяти минут — ошибка (допуск на синхронизацию часов, не на
будущие наблюдения). Будущее `price_timestamp` относительно экспорта запрещено.
Экспорт не может передвинуть `exportedAt` назад. Для Yahoo не придумывается время.
Заголовки, основания и единицы прежнего снимка сохраняются, источники сверяются с
фиксированным контрактом. `scripts/static-document.mjs` не изменён.

HTTP имеет таймаут 20 секунд, редиректы запрещены. Ошибки не печатают ключи,
заголовки запросов или тела ответов API. После полной проверки пишется временный
файл рядом со снимком, затем выполняется атомарное переименование. Ошибка до
переименования оставляет исходный файл побайтно прежним и исключает коммит.

Перед коммитом кандидат проходит `npm ci`, `npm test`, `typecheck`, `lint`, `build`
и Deno-проверку Edge Functions. Разрешено изменение **только** `data/snapshot.json`.
Если `main` сдвинулся после checkout — остановка без коммита; гонка после проверки
будет отклонена обычным push. Force push и rebase/retry запрещены. Для App 5872216
владелец настроил исключение только из PR/status-check ruleset `main-2`; запрет
удаления и force push в `main-1` остаётся без исключений. Сам workflow правила не
меняет. Если push отклонён, задача завершится ошибкой без альтернативного токена.

Все проверки выполняются **до** коммита в этой же задаче. Финальный push использует
короткоживущий токен приложения, а не `GITHUB_TOKEN`; только он получает Contents:
write для `market-pulse1`. `GITHUB_TOKEN` read-only и не сохраняется в checkout.
App-authenticated push может запускать GitHub Actions и Vercel Git integration;
это не отменяет проверки до отправки и не доказывает будущую публикацию HTML.

## Ручное добавление ключа — без пересылки в чат

1. Откройте [Market Pulse → Project Settings → API Keys](https://supabase.com/dashboard/project/hekzplfftannlzwvgwwm/settings/api-keys).
2. В разделе **Publishable and secret API keys** найдите **уже существующий Publishable
   key**, который используется сайтом. Скопируйте именно значение, начинающееся с
   `sb_publishable_`, кнопкой копирования рядом с ключом. Не создавайте новый ключ.
   **Не используйте** Secret key (`sb_secret_`), `service_role`, пароль базы или JWT
   из раздела legacy service role. Скрипт отвергает эти форматы.
3. Откройте [репозиторий → Settings → Secrets and variables → Actions](https://github.com/Clincher1/market-pulse1/settings/secrets/actions).
4. На вкладке **Secrets**, в секции **Repository secrets**, нажмите **New repository
   secret** ([прямая форма](https://github.com/Clincher1/market-pulse1/settings/secrets/actions/new)).
5. В **Name** введите точно `SNAPSHOT_SUPABASE_READ_KEY`. В **Secret** вставьте только
   скопированное значение ключа — без кавычек, `Bearer`, имени переменной и пробелов.
6. Нажмите **Add secret**. Если запись уже существует, используйте **Update** для неё.
   Нужен repository secret, не environment secret: workflow не использует environments.
   Не вставляйте значение в issue, PR, чат, YAML или файл репозитория.
7. На вкладке [**Variables**](https://github.com/Clincher1/market-pulse1/settings/variables/actions)
   проверьте repository variable `SUPABASE_URL`. Если её нет, нажмите **New repository
   variable**, Name: `SUPABASE_URL`, Value: `https://hekzplfftannlzwvgwwm.supabase.co`,
   затем **Add variable**. URL не является секретом. Если запись есть — значение должно
   совпадать с этим проектом.
8. После отдельного одобрения и слияния PR откройте **Actions → Update static snapshot →
   Run workflow**, выберите **main** и нажмите **Run workflow**, либо дождитесь расписания.
   Добавление секрета само по себе не запускает workflow; до мержа расписание этой
   ветки не активно. Агент этот PR не сливает.

Publishable-ключ остаётся публичным ключом с прежними правами `anon`; название GitHub
Secret не делает его отдельной изолированной CI-учётной записью. Результат RPC публичен
для держателей ключа, как и согласовано владельцем.

## Граница доступа Supabase и проведённая проверка

Миграция `20261122071543_static_snapshot_rpc.sql` **уже применена** к Market Pulse
(`hekzplfftannlzwvgwwm`) через миграционный API. Повторно вручную применять SQL не нужно.
История миграций содержит то же имя и версию; файл содержит точный применённый SQL.

- `static_snapshot_reader`: NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE,
  NOINHERIT, NOREPLICATION, NOBYPASSRLS; нет CREATE в `public` и прав записи.
- Роль получает только необходимые столбцы SELECT двух исходных таблиц. На обеих
  включён RLS; две SELECT-политики ограничены тремя ID.
- `SECURITY DEFINER` RPC принадлежит этой роли, имеет ноль аргументов,
  `search_path=''`, `row_security=on`, статический SQL без динамических имён.
- Клиентские `anon`/`authenticated` не члены технической роли. Им дан EXECUTE новой
  функции, но не SELECT исходных таблиц. Административный `postgres` не является
  клиентским доступом; его существующее администрирование ролей не ограничивается.
- Отпечаток всех прежних публичных column grants до/после совпал:
  `d2e077af641c37a77bc8cd0828674375`. Каталог подтвердил отсутствие SELECT/INSERT/
  UPDATE/DELETE/TRUNCATE исходных таблиц у клиентов и отсутствие записи у новой роли.
- [Реальная проверка с ключом сайта](https://github.com/Clincher1/market-pulse1/actions/runs/44997565766)
  завершилась успешно: RPC → три инструмента с числовыми строками, SELECT и безопасные
  INSERT/UPDATE/DELETE-пробы обеих исходных таблиц → HTTP 401/403 и SQLSTATE 42501;
  закрытый `source_url` старого history view остаётся закрытым; прежние запросы сайта
  к истории и cached_assets работают. INSERT использует пустой массив, UPDATE/DELETE —
  невозможные ID, то есть реальные строки не меняются даже при регрессии прав.
- `.github/workflows/snapshot-access.yml` повторяет проверку в PR/ветке. Также вызывает
  настоящий updater с живой RPC, но **только во временный файл**, без коммита/изменения
  снимка репозитория и без использования runtime-секрета.

## Публикация и оставшаяся сквозная проверка

Vercel Git integration действительно подключена к `Clincher1/market-pulse1`, production
branch — `main`. Наблюдались production READY/PROMOTED для `751d613` и автоматический
preview READY для первого коммита этой ветки `4766d7b`. Настройки интеграции не менялись,
новые токены или deploy hooks не добавлялись.

Это подтверждает обычный Git-based deployment, **но не доказывает** публикацию первого
будущего snapshot-коммита от App. Прежний ручной прогон 45003492254 прошёл проверки
и локальный commit, но push от GITHUB_TOKEN был отклонён защитой. Новый App push и
публикация нового HTML ещё не проверены: требуется отдельное слияние изменения
и ручной запуск владельца. Агент не запускает основной workflow без указания.
После первого успешного обновления нужно сверить SHA коммита снимка с production
Vercel READY/PROMOTED и проверить в исходном HTML главной новый `exportedAt` и три
наблюдения. Успешный коммит не следует выдавать за уже опубликованный HTML. Если push
или Vercel не запустился — это отдельная видимая ошибка, без автоматического обхода
защит/повышения прав. Одна успешная проверка не является заявлением о стабильности.
