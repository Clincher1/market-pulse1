# Резервное копирование Market Pulse

## Статус — не путать реализацию с созданной production-копией

Новый механизм реализован и проверен на **изолированной синтетической базе**:
12 таблиц / 96 строк, PostgreSQL 16.2 локально. Выполнены настоящий `pg_dump`,
`pg_restore`, сверка числа и содержимого строк, шифрование, расшифрование и
проверка SHA-256 дампа. Это не копия production. Отдельный CI проверяет тот же
сценарий на PostgreSQL 17, соответствующем major-версии production.

Production-копия считается созданной **только после успешного production job
и наличия его `.mpbackup` artifact**. Исторические зелёные запуски с пропущенной
выгрузкой не засчитываются. Issue #132 остаётся открытым до такого результата.

При подготовке защищённое подключение БД в workspace отсутствовало, а GitHub
ответил `403 Resource not accessible by integration` на чтение метаданных
Actions secrets. Это ограничение разрешений интеграции, не повод извлекать
пароли из vault, печатать ключи, делать базу публичной или менять пароль БД.
Подключённый Supabase SQL-коннектор не передаёт строку подключения процессу
`pg_dump` в GitHub runner. Нужен существующий защищённый runtime secret
`SUPABASE_DB_URL`; значение не передавать в чат/Git/логи.

## Что теперь делает workflow

`.github/workflows/backup-history.yml` задаёт ежедневное расписание 03:30 UTC
(расписание GitHub работает из default branch; открытый PR сам по себе его не
включает), ручной запуск и проверочный push на текущей рабочей ветке.

1. Отсутствие защищённого подключения немедленно завершает job ошибкой.
2. Открывается **READ ONLY / REPEATABLE READ** транзакция. Экспортированный
   snapshot используется и для `pg_dump`, и для подсчёта/хеширования строк.
   Данные не сравниваются с изменившейся базой «после выгрузки».
3. Сохраняются полный логический дамп схемы `public` и её данных, включая
   закрытые оригиналы. Реестр инструментов и `legacy_gold_cache_20261121` входят
   в обязательный набор; новые обычные public-таблицы обнаруживаются автоматически.
   Partitioned/foreign tables останавливают job до явного расширения покрытия.
4. В **одноразовом локальном PostgreSQL** создаются bare-таблицы и загружаются
   только записи `TABLE DATA`. Содержимое каждой таблицы и число строк должны
   совпасть с исходным snapshot. Рабочие триггеры, cron и функции не исполняются:
   они могли бы изменить исторические строки или вызвать внешних писателей.
5. Манифест содержит версии, commit, времена, SHA-256 дампа, имена/числа/хеши
   таблиц и время восстановления данных. Манифест также зашифрован.
6. Дамп и манифест упаковываются и шифруются AES-256-GCM; случайный ключ данных
   защищается RSA-4096 OAEP/SHA-256. Приватный ключ не нужен backup runner.
7. В GitHub artifact попадает **только `.mpbackup` ciphertext**, хранение 14 дней.
   Незашифрованные SQL/дамп/манифест/ключ не загружаются. Пустая загрузка — ошибка.
8. Ошибка любого шага не превращается в зелёный результат. Полные ошибки SQL
   не публикуются: они могут содержать строки истории или параметры подключения.

Это бесплатный путь в рамках существующих GitHub Actions/artifact лимитов.
Реальные размер, трафик и время production-выгрузки нужно измерить по первому
успешному запуску; лимиты и долговременный SLA не считаются доказанными заранее.
14-дневный срок хранения не означает наличие уже накопленных 14 копий.

## Ключ восстановления хранится отдельно

- В Git лежит **только публичный** `config/backup-recipient.pem`.
- Приватный ключ и автономный decrypt-инструмент сохранены в подключённом
  Dropbox владельца: `/Market Pulse Recovery/market-pulse-recovery-kit.zip`.
- При создании папка не имела `shared_folder_id`; публичная ссылка и приглашения
  не создавались. Content hash загруженного kit сверён с локальным.
- Публичный fingerprint получателя:
  `563c208f64d46c3e151c4598911ac5c1175cbc51f3c7d97adea0666bd459858c`.
- Не переносить recovery kit в GitHub artifacts, Git или публичную ссылку.
  Не ротировать и не удалять ключ, пока существуют копии, требующие старого ключа.
  Потеря приватного ключа делает расшифрование невозможным.
- `.local`, `.venv`, дампы, ciphertext и временные файлы исключены из Git.

## Порядок восстановления — только в отдельную среду

1. Взять artifact **из доверенного успешного production job этого репозитория**.
   Публичный recipient обеспечивает конфиденциальность и проверку повреждения,
   но не является цифровой подписью отправителя. Не принимать неизвестный файл
   только потому, что его удалось расшифровать.
2. Получить kit из своего Dropbox. Команда автономного инструмента:
   `node backup-envelope.mjs decrypt input.mpbackup recovery.tar private.pem`.
   Выходной файл должен отсутствовать; при ошибке аутентификации пригодный
   plaintext-файл не выдаётся. Не печатать ключ.
3. Проверить состав архива, манифест, `dump_sha256`, `fixture=false` и версии.
   Никогда не принимать `fixture-*.mpbackup` за production-копию.
4. Поднять отдельную совместимую Supabase/PostgreSQL среду, **не production**.
   Полный `public.dump` хранит схему/функции/представления/триггеры/данные public;
   восстановить зависимости Supabase, роли, расширения и политики согласно
   миграциям, затем загрузить оригиналы без выполнения рабочих писателей.
5. Повторно сверить таблицы, числа строк и содержимое с манифестом; отдельно
   проверить RLS/grants, публичные представления, выдачу сайта и API. Не включать
   cron/поставщиков/выпуск прогнозов автоматически.
6. Только после проверки планировать переключение. Не накатывать старый дамп на
   работающую базу и не повторять применённые миграции.

## Чего именно этот механизм не доказывает

Автопроверка подтверждает **восстановимость табличных данных public**, а не
полный перенос всей платформы Supabase: Auth, Storage, Vault, секреты, роли,
планировщик, Edge Functions и настройки Vercel лежат вне этого дампа/дрилла.
Их нельзя объявлять восстановленными по одному `pg_restore --data-only`.
Миграции и код в Git необходимы, но не заменяют данные.

Production RTO/RPO и full-platform recovery остаются неизмеренными до реального
разрешённого упражнения. Плановая частота — раз в сутки; пропуск job увеличивает
потенциальную потерю данных. Не обещать «никогда ничего не потеряется».
