# Диагностика commit/push статического снимка

Область изменения: только диагностика четырёх финальных этапов workflow. Нет
изменений снимка, Supabase, валидации данных или правил защиты GitHub. Этот PR
не запускает `Update static snapshot` и не заменяет ожидаемый ручной запуск владельца
после отдельного слияния PR.

## Что проверено о двух предполагаемых причинах

### 1. Объявленные права токена

В `.github/workflows/update-static-snapshot.yml` **уже до этого изменения** были:

```yaml
permissions:
  contents: read

jobs:
  refresh:
    permissions:
      contents: write
```

Отсутствие явного `contents: write` не является причиной: оно уже задано только
для `refresh`. Добавлять write на уровне всего workflow не нужно. Никакие новые
права (`actions`, `pull-requests`, administration) не запрошены. GitHub-интеграция
агента и runtime `GITHUB_TOKEN` job — разные субъекты с разными правами.

Локальный `git commit` не требует GitHub-токена: он требует корректной git identity
и доступного индекса. Токен нужен для авторизации `push`. Наличие декларации write
не доказывает, что сервер разрешит push при действующих правилах защиты.

### 2. Защита main

Read-only запрос `GET /repos/Clincher1/market-pulse1/branches/main` подтвердил:

- `protected: true`, `protection.enabled: true`;
- обязательный status check `verify`, приложение GitHub Actions (`app_id: 15368`);
- `enforcement_level: non_admins` в сокращённом ответе.

Полные настройки `GET .../branches/main/protection` недоступны интеграции:
**403 Resource not accessible by integration**. Read-only запрос
`GET .../rules/branches/main` вернул `[]`: это не отменяет подтверждённую classic
branch protection. Требование PR, ограничения push, исключения для сервисов и
полный список правил из доступного ответа установить нельзя.

**Защита включена, но категоричный вывод «все прямые push запрещены» и точная
причина первого сбоя пока не подтверждены.** Проверки кандидата выполняются до
создания нового коммита; это само по себе не создаёт GitHub status check `verify`
на SHA будущего коммита. Поэтому обязательный check может препятствовать такому
прямому push. Серверный отказ будет классифицирован отдельно, без изменения правил.

Никаких изменений защиты, токенов, исключений или прав интеграции не выполнено.

## Что покажет следующий ручной запуск

1. **Check changed files (snapshot only)** — только списки путей tracked/staged/
   untracked; явная причина отказа, если есть что-либо кроме `data/snapshot.json`.
   Неожиданные staged/untracked файлы запрещены. При отсутствии изменений остальные
   три этапа пропускаются.
2. **Check main is still current** — успешность fetch, исходный SHA, SHA именно
   fetched `main` (`FETCH_HEAD`) и локальный HEAD. Сдвиг main/HEAD останавливает
   выполнение до коммита. Проверка FETCH_HEAD не зависит от состояния remote-tracking
   ref после fetch; конфликты не исправляются автоматически.
3. **Commit validated snapshot locally** — повторная проверка allowlist перед
   staging, проверка единственного staged пути, отдельный результат commit и SHA.
   Успешный локальный commit ещё не означает успешную публикацию.
4. **Push snapshot commit (no force or bypass)** — один обычный
   `git push origin HEAD:main`. При отказе: код выхода и категория (branch protection/
   rules; non-fast-forward; auth/permission; прочее). Нет retry, force, rebase,
   альтернативного токена или обхода защиты. Неизвестный отказ не объявляется
   доказанной проблемой прав.

Все результаты есть в Actions **Summary** и в отдельных шагах. Не печатаются
ключи, переменные окружения, git config/remote URLs, тела ответов Supabase или raw
remote output. Временный вывод push используется только для классификации и
удаляется при завершении шага; он не загружается в artifacts. Ошибка fetch даёт
код выхода без потенциально чувствительных remote details.

## Если защита действительно блокирует push — выбор владельца

**Рекомендуемый вариант: PR от бота.** Автоматизация создаёт snapshot-only ветку и PR,
проверки выполняются для её SHA, затем обычное ревью/слияние по существующим правилам.
Понадобятся отдельно согласованные права `pull-requests: write` и настройка запуска
проверок: события от `GITHUB_TOKEN` обычно не вызывают новые Actions. Это не реализовано
в диагностическом PR и не означает автоматический merge.

**Альтернатива: узкое исключение для выделенного сервиса/GitHub App.** Только если
владелец сознательно выберет прямой push: отдельная учётная запись сервиса, минимальные
права на этот репозиторий и точечное правило исключения, без общего снятия защиты.
Это увеличивает полномочия сервиса и требует отдельного согласования/настройки;
текущий токен не заменён, исключения не добавлены.

До выбора владельца оба варианта остаются предложениями. Для диагностики достаточно
ручного запуска текущей модели workflow; **не следует отключать защиту ради теста**.
