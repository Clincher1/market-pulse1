# Самостоятельная проверка перед публикацией

Эта инструкция — практический чек-лист для локальной проверки Market Pulse. Она не обещает,
что ошибок не будет: проверки помогают увидеть их до выкладки и понять, на каком этапе они
возникли. Для правил наблюдаемого доказательства и проверки данных во времени см.
[`VERIFICATION-METHOD.md`](VERIFICATION-METHOD.md).

## 1. Убедиться, что проверяется нужная копия

Откройте терминал **в корне репозитория** и выполните:

```bash
git rev-parse --show-toplevel
git branch --show-current
git status --short
git diff --check
node --version
npm --version
```

Для проекта нужна Node.js **22.x**. Сверьте ветку и список изменённых файлов с задачей. Не
запускайте `git reset`, `git clean` или очистку рабочей папки, чтобы «починить» тесты: это может
удалить незакоммиченные изменения.

Каноническая опубликованная версия —
[Clincher1/market-pulse1 на `main`](https://github.com/Clincher1/market-pulse1/tree/main).
Рабочая ветка может ещё не совпадать с сайтом.

## 2. Установить ровно зафиксированные зависимости

Из корня репозитория:

```bash
npm ci
```

`npm ci` устанавливает версии из `package-lock.json`. Для обычной проверки не заменяйте его на
`npm install` и не запускайте `npm audit fix`: последнее может обновить lock-файл и создать
отдельный набор изменений.

Убедитесь, что команды действительно установлены:

```bash
test -x node_modules/.bin/tsc && echo 'TypeScript установлен'
test -x node_modules/.bin/eslint && echo 'ESLint установлен'
```

Если появляется `tsc: not found` или `eslint: not found`, проверка кода ещё не началась: в этой
копии нет dev-зависимостей. Выполните `npm ci` снова **в том же рабочем каталоге**. В Arena
`node_modules` исключён из сохранённых снимков, поэтому после отдельного восстановления сессии
его отсутствие возможно; это не исправляется правкой исходников.

## 3. Запустить проверки по очереди

После успешного `npm ci` выполните из корня:

```bash
npm run typecheck
npm run lint
npm test
npm run build
(cd supabase/functions && npx -y deno@2 check */index.ts _shared/*.ts)
git diff --check
```

Запускайте их последовательно, не параллельно. Если команда вернула ненулевой код — этап **не
пройден**; сначала исправьте конкретное сообщение и повторите полный список. `npm run build`
включает TypeScript-проверку ещё раз и затем собирает production bundle. Команда Edge Functions
проверяет Deno-код и не заменяется успешным `npm run build`.

Для быстрой первичной проверки можно выполнить только `npm run typecheck`, `npm run lint` и
`npm test`, но такой результат нельзя называть полной проверкой перед выкладкой без сборки и
проверки Edge Functions.

## 4. Проверить изменения глазами

Зелёные тесты не доказывают, что подпись правдива или что нужный экран виден пользователю.
После успешной сборки:

1. Запустите `npm run dev` и откройте показанный локальный адрес.
2. Проверьте затронутый экран, пустое состояние и ошибку загрузки.
3. Сверьте значения, источник, инструмент, единицы и даты с теми же данными, из которых их
   считает интерфейс. Если менялась арифметика, пересчитайте её по отображённым точкам.
4. Проверьте, что в консоли браузера нет ошибок. Предпросмотр Vercel полезен для проверки
   внешнего вида, но не заменяет тесты, typecheck и проверку источников.
5. Если утверждается стабильность источника или расписания, соберите наблюдения за период,
   а не один успешный ответ. Методика — в [`VERIFICATION-METHOD.md`](VERIFICATION-METHOD.md).

## 5. Использовать бесплатный CI в GitHub

В `.github/workflows/quality.yml` находится отдельная проверка без выкладки и без секретов.
Она запускается на push в рабочие ветки, на pull request в `main` и вручную. В GitHub откройте
**Actions → Quality checks**: у каждого шага есть отдельный результат и журнал.

Чтобы красная проверка не проходила незаметно, владелец репозитория может в настройках GitHub
добавить branch rule для `main` и включить обязательную status check `Quality checks / verify`.
Проверка в Actions сама по себе лишь сообщает результат; обязательность задаётся правилом
ветки. Публичный сайт и его Vercel Preview не являются заменой CI.

CI нужен для раннего сигнала, а не для гарантии безошибочности. Он не проверяет автоматически
смысл каждого нового текста, правильность внешних источников во времени, состояние production
БД или то, что конкретная правка уже выложена. Такие проверки делаются отдельно и описываются
по наблюдаемому результату.

## 6. Как читать типичные ошибки

- `tsc` / `eslint: not found` — отсутствуют зависимости; начните с `npm ci`.
- Ошибка TypeScript — типы и фактическая структура данных не совпали; не исправляйте её
  принудительным `any` или удалением проверки.
- `npm test` упал — прочитайте первый `not ok`, файл и строку. Не ослабляйте assertion, пока
  не установлено, что именно стало неверным: код, тест или ожидаемый контракт.
- `npm run build` упал до сообщения Vite — обычно сначала падает TypeScript-проверка; исправьте
  её и повторите.
- Ошибка Deno — проверяйте Edge Function отдельно приведённой командой; зелёный frontend build
  ничего не говорит о компиляции функций.
- `npm ci` сообщил об уязвимостях — это отдельный отчёт dependency audit, не доказательство
  того, что текущие тесты или сборка упали. Сохраните вывод `npm audit` для отдельного разбора;
  не запускайте автоматическое обновление пакетов без отдельной проверки.

В сообщении о результате указывайте ветку, команды, коды выхода и первую ошибку каждого
неуспешного этапа. Не называйте проверку пройденной, если её вывод не был получен.
