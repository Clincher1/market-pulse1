# Проверка защиты истории — результат текущей доработки

## Вердикт

Механизм резервного копирования реализован и проходит recovery-регрессию на
изолированных тестовых данных. **Production-копия ещё не создана: в GitHub
runner не настроено защищённое подключение БД.** Сайт и production-история в
этой задаче не изменялись. PR #131 не слит, issue #132 остаётся открытым.

## Что сделано

- Полный логический дамп `public`, включая данные закрытых таблиц и реестр
  инструментов; обязательна сохранённая исходная история золота.
- Snapshot и контрольные суммы снимаются в одной read-only repeatable-read
  транзакции. Рабочие записи не меняются.
- Перед сохранением копии табличные данные восстанавливаются в отдельный
  локальный PostgreSQL; сравнивается не только число, но и содержимое строк.
- Триггеры/писатели не исполняются во время проверки восстановления.
- Дамп с манифестом шифруется AES-256-GCM + RSA-OAEP/SHA-256 (RSA-4096).
  В artifacts разрешён только ciphertext `.mpbackup`, не plaintext и не ключ.
- Приватный recovery kit сохранён в Dropbox владельца:
  `/Market Pulse Recovery/market-pulse-recovery-kit.zip`.
  Публичная ссылка/приглашения не создавались. Dropbox content hash совпал с
  локальным: `5e95db4c36bd99e91f63810daedcdcf335df1ad225b13f51bc6e61c069ed4651`.
  Сам ключ не помещался в Git, чат или Actions.
- Отсутствие подключения, повреждение ciphertext, неправильный ключ,
  удалённая/непустая restore-цель завершаются ошибкой, а не зелёным пропуском.
- Расписание в коде: ежедневно 03:30 UTC, хранение 14 дней. GitHub запускает
  расписание из default branch, поэтому открытый PR его ещё не активирует.

## Что необходимо для завершения

В workspace защищённого подключения нет. GitHub API на метаданные secrets
возвращает `403 Resource not accessible by integration`, поэтому текущая
интеграция не может самостоятельно проверить/настроить `SUPABASE_DB_URL`.
Коннекторы Supabase и Dropbox не дают `pg_dump` в GitHub runner доступ к БД.
Пароли в чат не запрашиваются, credentials из vault не извлекаются, права
публичного пользователя не расширяются, пароль рабочей БД не меняется.

Нужна настройка runtime connection через разрешённый защищённый канал владельца
GitHub Actions, затем успешный production job и проверка наличия его ciphertext.
Только после этого можно подтвердить первую копию, измерить реальный размер,
время и трафик и согласовать включение расписания через merge PR.

Recovery-drill проверяет **табличные данные public**, а не полную платформу
Supabase/Auth/Storage/Vault/секреты/cron. Полный перенос платформы и долгосрочные
RTO/RPO не сертифицированы. Порядок действий и границы — в `docs/BACKUP.md`.
