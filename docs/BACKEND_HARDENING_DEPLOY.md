# Backend hardening: порядок деплоя (подготовлено 2026-10-22)

Статус на 2026-10-22: **подготовка завершена, код функций ещё не задеплоен**.
По отчёту владельца секрет уже создан в Vault, добавлен в Edge Function Secrets,
а все четыре pg_cron-задачи уже отправляют `x-cron-secret`. Поэтому шаги 1–3 ниже
уже выполнены; остался деплой кода и проверка. Коннектор Supabase в Arena 22.10
вернул Authentication failed (401), поэтому автоматический деплой из чата временно
недоступен до повторной аутентификации коннектора.

## Что подготовлено

| Артефакт | Что делает |
|---|---|
| `supabase/functions/update-assets/index.ts` | Добавлена проверка `isAuthorizedCron` в начале обработчика |
| `supabase/functions/update-tension/index.ts` | Та же проверка + консервативная дедупликация выборки |
| `supabase/functions/update-forecasts/index.ts` | Та же проверка + консервативная дедупликация сигналов |

Проверка принимает **либо** `Authorization: Bearer <service_role>`, **либо** заголовок
`x-cron-secret`, равный секрету функции `CRON_SECRET`. Все остальные вызовы получают **401**.
Сравнение секрета — constant-time.

4. ⏳ **Задеплоить три пропатченные функции** (`update-assets`, `update-tension`,

## update-news

Полного исходника в репозитории нет, а задеплоенный код виден в Supabase в
минифицированном виде. Для него подготовлен отдельный точный патч:
`supabase/functions/update-news/CRON_AUTH_PATCH.md`.

Он вставляется первым оператором обработчика, принимает service-role bearer
или `x-cron-secret`, сравнивает секрет в constant-time и возвращает 401 до
любого сбора новостей и вызова Groq. Восстанавливать весь `update-news` из
минифицированного кода ради одной проверки не нужно и рискованнее.

До деплоя этого патча `update-news` остаётся публично вызываемой — это
известный остаточный риск расхода квоты Groq.

## Что сознательно НЕ включено

- **Расписание V2 shadow** лежит в том же SQL (Part B), но закомментировано:
  по плану сначала малые батчи классификаций и ручной аудит качества, потом cron.
- `verify_jwt` у legacy-функций не трогаем: защита делается в коде, чтобы pg_net
  мог ходить без JWT, а авторизацию давал `x-cron-secret`.
- Удаление дубля секрета `SERVICE_KEY` — после того, как убедимся, что все функции
  читают `SUPABASE_SERVICE_ROLE_KEY` (отдельная маленькая задача этапа 5).
