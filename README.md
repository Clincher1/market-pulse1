# Market Pulse

Публичный дашборд рыночных значений и заголовков публикаций. Для чисел показываются
источник, дата/время и единицы; производные значения должны быть пересчитываемы по
напечатанным рядам. Сайт не выводит причинность из совпадения новости с движением цены.

**Канонический репозиторий:** [Clincher1/market-pulse1 на `main`](https://github.com/Clincher1/market-pulse1/tree/main)
**Публичный сайт:** <https://market-pulse1-eta.vercel.app/>

## Что сейчас показывает интерфейс

- Российские и мировые рыночные значения с подписью инструмента, источника, даты и единиц.
- Источники, формулы и правила показа заданы кодом. Котировки приходят от поставщиков,
  изменения считаются по опубликованным рядам, не моделью.
- В новостной ленте — исходные заголовки, источник, время и ссылка. Серверная обработка
  некоторых новых публикаций использует модели; оценки скрыты и не определяют порядок ленты.
  Если модель не ответит, публикация может не попасть в кэш.
- Архив прогнозов не входит в текущую публичную навигацию; новые прогнозы не выпускаются.
  Исторические записи сохраняются в базе.

Индекс новостной напряжённости не входит в публичный интерфейс. Его старые таблицы и
серверная история не удаляются этой работой. Не переименовывать старую метрику в «долю
негатива» и не добавлять вместо неё новый индекс.

## Стек и данные

- React, TypeScript, Vite, Tailwind CSS, Framer Motion.
- Supabase Postgres: read-only кэш для браузера и отдельные публичные представления
  архивных данных; RLS/публичные grants задаются на стороне Supabase.
- Vercel: приложение и серверные API (`api/russia-insights.js`,
  `api/russia-history.js`, `api/brief-image.js`). Внешние источники опрашиваются
  с серверной стороны и не должны блокировать остальные данные.
- Supabase Edge Functions: исходный код в `supabase/functions/`; расписания и секреты
  не следует переносить в браузер.

В браузере нет cookies, аналитики, телеметрии или SDK мониторинга. Техническая
наблюдаемость — серверная. Используются бесплатные тарифы; не добавляйте платный
провайдер без явного решения владельца.

### Реестр секретов и ротация

Здесь перечислены только имена, назначение и место использования; значения секретов
не должны попадать в README, логи или коммиты. Разделение GitHub Actions, Supabase
Edge Functions и Vercel подтверждается workflow-файлами и исходниками; наличие,
срок действия и актуальность каждого значения проверяются владельцем в соответствующей
панели.

| Секрет/настройка | Где хранится и используется | Действие / ротация |
| --- | --- | --- |
| `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF` | GitHub Actions; `deploy-functions.yml` и `deploy-shadow.yml` для публикации Edge Functions | Владелец должен определить и записать политику срока действия access token. Старый `market-pulse-github-actions` token отзывать только после подтверждённого успешного запуска deploy с `main`. |
| `SUPABASE_DB_URL` | GitHub Actions; только `backup-history.yml` для read-only backup | Считать production credential: минимальные права, ротация при утечке/смене владельца, не помещать в диагностические выводы. |
| `SNAPSHOT_SUPABASE_READ_KEY` | GitHub Actions; snapshot update, watchdog и ограниченная PR-проверка доступа | Только read-only RPC-доступ; не использовать service-role ключ. |
| `SNAPSHOT_APP_PRIVATE_KEY` (с `SNAPSHOT_APP_ID`) | GitHub Actions; финальный push snapshot-артефактов приложением GitHub App | Ограничить репозиторием и необходимыми правами; не расширять токен на тесты/сборку. `SNAPSHOT_APP_ID` — идентификатор, не секрет. |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TG_OWNER_CHAT_ID` | GitHub Actions; ошибки workflow, selfcheck и уведомления владельцу | Бот-токен и chat IDs не выводить в логи; сверять, что bot и получатель соответствуют нужной среде. |
| `LINEAR_API_KEY` | GitHub Actions; только запись issue при ошибках deploy | Проверить, что integration и права остаются необходимыми; не использовать в приложении. |
| `SUPABASE_SERVICE_ROLE_KEY` / `SERVICE_KEY` | Supabase Edge Function secrets; backend-функции с доступом к БД | Привилегированный серверный credential. В коде есть оба имени как runtime alias; браузерный `VITE_*` экспорт запрещён. |
| `CRON_SECRET` | Supabase Edge Function secrets и отдельно в конфигурации вызывающего `pg_cron` HTTP-заголовка | Ротировать в обеих точках в одной согласованной операции: обновить вызывающую сторону и функции без промежутка с несовпадающими значениями. |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Supabase Edge Function secrets для selfcheck и `scheduled-job-runner` | Синхронизируются `deploy-functions.yml` из GitHub Actions; проверить доставку после ротации. |
| `HEALTHCHECK_PING_URL` | Необязательный Supabase Edge Function secret для `scheduled-job-runner` | Пока внешний аккаунт не создавался. Если владелец задаст URL позже, код отправляет ping только после успешной свежей дневной доставки; `/fail` — при DB/Telegram 5xx; unset — тихо отключено. |
| `SUPABASE_SERVICE_KEY` | В исходниках не найдено прямого чтения именно этого имени (не путать с `SERVICE_KEY`) | Владелец должен проверить Supabase Function secrets и удалить только после подтверждения, что ни одна активная функция/интеграция его не использует. |
| `ADMIN_TRIGGER_KEY` | Ранее — Vercel для удалённого channel-trigger endpoint | Endpoint удалён. Три переменные Vercel `ADMIN_TRIGGER_KEY` (production, preview, development) были удалены; проверить, что конфигурация панели совпадает. |

**Открытые действия владельца:** зафиксировать expiration policy для
`SUPABASE_ACCESS_TOKEN`; дождаться подтверждённого deploy-запуска с `main` перед
отзывом старого `market-pulse-github-actions`; проверить и при подтверждённой
неиспользуемости удалить `SUPABASE_SERVICE_KEY`; согласовать и одновременно ротировать
`CRON_SECRET` в Supabase и в caller-конфигурации. Эти административные проверки не
можно достоверно выполнить только по коду репозитория.

## Локальный запуск

Требуется Node.js 22.

```bash
npm ci
npm run dev
```

Переменные окружения описаны в `.env.example`. Для Supabase в браузере допустим только
публичный publishable/anon key при read-only RLS; service-role ключи и другие секреты
никогда не помещаются в `VITE_*`.

## Проверки

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run build
(cd supabase/functions && npx -y deno@2 check */index.ts _shared/*.ts)
git diff --check
```

Выполняйте шаги по очереди. Пошаговый разбор локальных и GitHub Actions проверок —
[`docs/SELF-CHECK.md`](docs/SELF-CHECK.md). Стабильность оценивается по серии наблюдений за
временное окно, не по одному зелёному запуску. Критерии доказательной проверки — в
`docs/VERIFICATION-METHOD.md`.

## Правила для изменений данных

- Сначала определить конкретное поле, источник, единицу и дату наблюдения.
- Не подменять отсутствующие данные резервными числами и не превращать модельную оценку
  в факт переименованием.
- Не удалять прогнозные или исторические строки из базы. Изменения БД — только миграциями;
  миграционный SQL хранится в `supabase/migrations/`.
- Выбор источника — вручную и только при наличии действительно эквивалентной замены.
  Не добавлять HTML-скрапинг без явного согласия владельца сайта.
- Для графиков указывать cadence/частоту наблюдений и не дорисовывать отсутствующие точки.

## Telegram-уведомления и watchdog

Уведомления отправляются напрямую через Telegram Bot API. В GitHub Actions добавьте
repository secrets `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Общий отправитель
`scripts/send-telegram.js` используется workflow-ами;
токен и chat ID не хранятся в исходниках и не выводятся в логи. При ответе Telegram с
ошибкой полный ответ API попадает в лог уведомляющего шага, но сам шаг настроен
`continue-on-error: true` и не меняет результат основной проверки.

`deploy-functions.yml` переносит эти два секрета в Supabase Edge Function secrets для
selfcheck. После успешной записи результата в `site_health` функция сообщает о новом
или изменившемся красном результате и об устранении ошибки; точный повтор неизменной
ошибки не дублируется. В устойчивом зелёном состоянии уведомления нет; сбой доставки
не меняет сохранённый результат.

Telegram-уведомления selfcheck дедуплицируются по имени проверки и точному тексту
ошибки: одинаковый неустранённый сбой сообщает один раз, новый или изменившийся сбой
сообщает сразу, восстановление всегда сообщает. Повторного периодического маркера для
неизменной ошибки нет.

Автоматические уведомления:

1. **Бэкап/обновление снимка** — при падении job `refresh` в конце
   `update-static-snapshot.yml` отправляется сообщение с именем job и кратким названием
   упавшего шага. Успешный запуск молчит.
2. **Сертификаты MOEX** — `check-moex-certificate-expiry.yml` запускается по понедельникам
   в 06:00 UTC. Проверяются live TLS-цепочка `iss.moex.com` и каждый сертификат в
   `certs/moex-ca-bundle.pem`; порог — 30 дней. При близком/истёкшем сроке или
   недоступности цепочки приходит сообщение с сертификатом и остатком дней (для
   недоступной цепочки срок неизвестен). Успешная проверка молчит.
3. **Selfcheck watchdog** — `selfcheck-watchdog.yml` запускается ежедневно в 06:05 UTC и
   читает последнюю зелёную запись `site_health`. Если она старше 26 часов или отсутствует,
   приходит сообщение с датой последней зелёной записи в UTC; при свежей записи — тишина.

Для чтения `site_health` watchdog использует `SUPABASE_URL` из repository variables и
`SNAPSHOT_SUPABASE_READ_KEY` из repository secrets. Для ручной проверки доставки без
искусственного сбоя откройте **Actions → Selfcheck watchdog → Run workflow** и включите
`telegram_test`: придёт отдельное тестовое сообщение с временем UTC, запись `site_health`
не меняется. Без этого флажка watchdog отправляет сообщение только при устаревшей или
отсутствующей зелёной записи. Успешные проверки не отправляют heartbeat-сообщения.

## Runbook: монитор и отчёты

- Edge Function `scheduled-job-runner` вызывается каждый час в `:12` UTC; cron использует `net.http_post` асинхронно.
- Дайджест обычно отправляется в 09:12 МСК (`DIGEST_HOUR_MSK`, по умолчанию `09`; запуск cron в 06:12 UTC). С 00:00 до заданного часа МСК (по умолчанию 09:00) отправка не запускается. Если попытка не удалась, доставка повторяется при каждом последующем часовом запуске в тот же московский день до успеха.
- Если дайджеста нет больше примерно 24 часов, считайте, что не работает вся цепочка мониторинга и уведомлений.

Свежесть Brent и золота учитывает сессии: во время торгов действует порог 2 часа, а при закрытом рынке достаточно обновления после открытия последней завершённой сессии. Для GLDRUB_TOM используется приближение пн–пт 09:00–23:50 МСК и упрощённый календарь российских праздников; календарь ICE не учитывает внутринедельные ранние закрытия, поэтому возможен редкий ложный сигнал устаревания.
- Для смены часа задайте секрет Edge Function `DIGEST_HOUR_MSK` числом от `00` до `23`; новые секреты токенов не нужны.
- Проверить планировщик и недавние SQL-запуски:

```sql
select j.jobname, j.schedule, d.start_time, d.end_time, d.status, d.return_message
from cron.job j
left join lateral (
  select * from cron.job_run_details r where r.jobid = j.jobid
  order by r.start_time desc limit 5
) d on true
where j.jobname = 'scheduled-job-runner'
order by d.start_time desc;
```

- `cron.job_run_details` показывает состояние SQL-вызова, а не HTTP-результат асинхронного `net.http_post`.
- Проверить коды Edge Function и тело ответа (последние записи):

```sql
select created, status_code, timed_out, error_msg, content
from net._http_response
order by created desc limit 20;
```

- `200` с `{"status":"fresh"}` означает штатный часовой монитор; `digest_sent` — отчёт отправлен.
- `401` означает отсутствующий/неверный секрет вызова; `503` — отсутствующий или некорректный Brent/временная метка.
- `5xx` означает сбой чтения БД, записи истории или доставки Telegram (повтор Telegram выполняется один раз через 5 секунд).
- При не-`2xx` сначала проверьте Supabase Function Logs и `net._http_response`; затем восстановите источник/доступность БД либо Telegram и повторите запрос авторизованно.
- Не трактуйте успешный `cron.job_run_details` как доказательство успешного HTTP-ответа: проверяйте обе таблицы.
