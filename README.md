# Market Pulse

Публичный дашборд рыночных значений и заголовков публикаций. Для чисел показываются
источник, дата/время и единицы; производные значения должны быть пересчитываемы по
напечатанным рядам. Сайт не выводит причинность из совпадения новости с движением цены.

**Канонический репозиторий:** [Clincher1/market-pulse1 на `main`](https://github.com/Clincher1/market-pulse1/tree/main)
**Публичный сайт:** <https://market-pulse1-eta.vercel.app/>

## Что сейчас показывает интерфейс

- Российские и мировые рыночные значения с подписью инструмента, источника, даты и единиц.
- Заголовки новостных публикаций: текст, источник, время публикации и ссылка. Модельные
  оценки важности, уверенности, тональности и предполагаемого влияния не показываются и не
  используются для отбора публичной ленты.
- Прозрачные изменения и сравнения, рассчитанные по указанным рядам.
- Архив прогнозных записей, созданных ранее. Новые прогнозы не выпускаются; исходные
  исторические строки не удаляются и не переписываются интерфейсом.

Индекс новостной напряжённости не входит в публичный интерфейс. Его старые таблицы и
серверная история не удаляются этой работой. Не переименовывать старую метрику в «долю
негатива» и не добавлять вместо неё новый индекс.

## Стек и данные

- React, TypeScript, Vite, Tailwind CSS, Framer Motion.
- Supabase Postgres: read-only кэш для браузера и отдельные публичные представления
  архивных данных; RLS/публичные grants задаются на стороне Supabase.
- Vercel: приложение и серверные API (`api/russia-insights.js`,
  `api/russia-history.js`, `api/brief-image.js`). Внешние источники опрашиваются
  с серверной стороны и не должны блокировать остальные данные.
- Supabase Edge Functions: исходный код в `supabase/functions/`; расписания и секреты
  не следует переносить в браузер.

В браузере нет cookies, аналитики, телеметрии или SDK мониторинга. Техническая
наблюдаемость — серверная. Используются бесплатные тарифы; не добавляйте платный
провайдер без явного решения владельца.

## Локальный запуск

Требуется Node.js 22.

```bash
npm ci
npm run dev
```

Переменные окружения описаны в `.env.example`. Для Supabase в браузере допустим только
публичный publishable/anon key при read-only RLS; service-role ключи и другие секреты
никогда не помещаются в `VITE_*`.

## Проверки

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run build
(cd supabase/functions && npx -y deno@2 check */index.ts _shared/*.ts)
git diff --check
```

Выполняйте шаги по очереди. Пошаговый разбор локальных и GitHub Actions проверок —
[`docs/SELF-CHECK.md`](docs/SELF-CHECK.md). Стабильность оценивается по серии наблюдений за
временное окно, не по одному зелёному запуску. Критерии доказательной проверки — в
`docs/VERIFICATION-METHOD.md`.

## Правила для изменений данных

- Сначала определить конкретное поле, источник, единицу и дату наблюдения.
- Не подменять отсутствующие данные резервными числами и не превращать модельную оценку
  в факт переименованием.
- Не удалять прогнозные или исторические строки из базы. Изменения БД — только миграциями;
  миграционный SQL хранится в `supabase/migrations/`.
- Выбор источника — вручную и только при наличии действительно эквивалентной замены.
  Не добавлять HTML-скрапинг без явного согласия владельца сайта.
- Для графиков указывать cadence/частоту наблюдений и не дорисовывать отсутствующие точки.

## Telegram-уведомления и watchdog

Уведомления отправляются напрямую через Telegram Bot API. В GitHub Actions добавьте
repository secrets `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Общий отправитель
`scripts/send-telegram.js` используется workflow-ами;
токен и chat ID не хранятся в исходниках и не выводятся в логи. При ответе Telegram с
ошибкой полный ответ API попадает в лог уведомляющего шага, но сам шаг настроен
`continue-on-error: true` и не меняет результат основной проверки.

`deploy-functions.yml` переносит эти два секрета в Supabase Edge Function secrets для
selfcheck. Функция отправляет сообщение только после успешной записи результата в
`site_health` и только если он красный: в Telegram перечисляются упавшие проверки и их
причины. При зелёном selfcheck уведомления нет; сбой доставки не меняет сохранённый
результат.

Автоматические уведомления:

1. **Бэкап/обновление снимка** — при падении job `refresh` в конце
   `update-static-snapshot.yml` отправляется сообщение с именем job и кратким названием
   упавшего шага. Успешный запуск молчит.
2. **Сертификаты MOEX** — `check-moex-certificate-expiry.yml` запускается по понедельникам
   в 06:00 UTC. Проверяются live TLS-цепочка `iss.moex.com` и каждый сертификат в
   `certs/moex-ca-bundle.pem`; порог — 30 дней. При близком/истёкшем сроке или
   недоступности цепочки приходит сообщение с сертификатом и остатком дней (для
   недоступной цепочки срок неизвестен). Успешная проверка молчит.
3. **Selfcheck watchdog** — `selfcheck-watchdog.yml` запускается ежедневно в 06:05 UTC и
   читает последнюю зелёную запись `site_health`. Если она старше 26 часов или отсутствует,
   приходит сообщение с датой последней зелёной записи в UTC; при свежей записи — тишина.

Для чтения `site_health` watchdog использует `SUPABASE_URL` из repository variables и
`SNAPSHOT_SUPABASE_READ_KEY` из repository secrets. Для ручной проверки доставки без
искусственного сбоя откройте **Actions → Selfcheck watchdog → Run workflow** и включите
`telegram_test`: придёт отдельное тестовое сообщение с временем UTC, запись `site_health`
не меняется. Без этого флажка watchdog отправляет сообщение только при устаревшей или
отсутствующей зелёной записи. Успешные проверки не отправляют heartbeat-сообщения.

## Runbook: монитор и отчёты

- Edge Function `scheduled-job-runner` вызывается каждый час в `:12` UTC; cron использует `net.http_post` асинхронно.
- Ежедневный Telegram-дайджест отправляется при первом запуске в `DIGEST_HOUR_UTC` (по умолчанию `06`, то есть обычно в 06:12 UTC).
- Для смены часа задайте секрет Edge Function `DIGEST_HOUR_UTC` числом от `00` до `23`; новые секреты токенов не нужны.
- Проверить планировщик и недавние SQL-запуски:

```sql
select j.jobname, j.schedule, d.start_time, d.end_time, d.status, d.return_message
from cron.job j
left join lateral (
  select * from cron.job_run_details r where r.jobid = j.jobid
  order by r.start_time desc limit 5
) d on true
where j.jobname = 'scheduled-job-runner'
order by d.start_time desc;
```

- `cron.job_run_details` показывает состояние SQL-вызова, а не HTTP-результат асинхронного `net.http_post`.
- Проверить коды Edge Function и тело ответа (последние записи):

```sql
select created, status_code, timed_out, error_msg, content
from net._http_response
order by created desc limit 20;
```

- `200` с `{"status":"fresh"}` означает штатный часовой монитор; `digest_sent` — отчёт отправлен.
- `401` означает отсутствующий/неверный секрет вызова; `503` — отсутствующий или некорректный Brent/временная метка.
- `5xx` означает сбой чтения БД, записи истории или доставки Telegram (повтор Telegram выполняется один раз через 5 секунд).
- При не-`2xx` сначала проверьте Supabase Function Logs и `net._http_response`; затем восстановите источник/доступность БД либо Telegram и повторите запрос авторизованно.
- Не трактуйте успешный `cron.job_run_details` как доказательство успешного HTTP-ответа: проверяйте обе таблицы.
